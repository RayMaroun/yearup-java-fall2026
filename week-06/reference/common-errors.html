Week 6 · Reference

Common Errors

The messages you will meet this week, word for word, and the quiet bugs that print no message at all. Read the first line of the message: it usually names the fix. In IntelliJ each compile message starts with java:.

Show
Compile

The parent has no constructor without parameters

See it
java: constructor Animal in class Animal cannot be applied to given types;
  required: String
  found:    no arguments
  reason: actual and formal argument lists differ in length

Every child constructor starts by calling a parent constructor. With no super(...) written, Java calls super(), and Animal only has Animal(String name). The error points at the child class, or at the child constructor if it has none of its own.

FixCall the parent constructor that exists, as the first statement, and pass what it asks for.

Before
public class Dog extends Animal {
    private String breed;
}
After
public class Dog extends Animal {
    private String breed;

    public Dog(String name, String breed) {
        super(name);
        this.breed = breed;
    }
}
Compile

super(...) is not the first statement

See it
java: call to super must be first statement in constructor

The parent has to be built before the child can add anything, so super(...) must come before every other line of the constructor, even a plain assignment.

FixMove the super(...) line to the top.

Before
public Dog(String name, String breed) {
    this.breed = breed;
    super(name);
}
After
public Dog(String name, String breed) {
    super(name);
    this.breed = breed;
}
Compile

A child uses the parent's private field

See it
java: name has private access in Animal

A child inherits a private field, but only Animal itself can name it. The child code has to go through the inherited getter or setter.

FixUse getName() and setName(...). Make the field protected only if the parent really wants its children to use it.

Before
public void bark() {
    System.out.println(name + " says: Ruff, ruff!");
}
After
public void bark() {
    System.out.println(getName() + " says: Ruff, ruff!");
}
Compile

Protected from a class outside the family

See it
java: favoriteFood has protected access in Animal

protected opens a member to child classes and to classes in the same package. A class in another package that is not a child is outside.

FixGo through a public getter or setter, or make the class a child of Animal.

Before
x.favoriteFood = "fish";  // class in another package
After
x.setFavoriteFood("fish");  // a public setter in Animal
Compile

@Override with no matching parent method

See it
java: method does not override or implement a method from a supertype

@Override asks the compiler to check the parent really has this method with this signature. The name or the parameters differ, so it refuses. Without the annotation this would compile and quietly become a new method.

FixMatch the parent's name and parameters exactly, or remove @Override if you meant a brand new method.

Before
@Override
public void eet() { ... }
After
@Override
public void eat() { ... }
Compile

An override with weaker access

See it
java: eat() in Caveman cannot override eat() in Human
  attempting to assign weaker access privileges; was public

A child may not hide a method more than the parent did. Human.eat() is public, so the override cannot be package-private.

FixWrite public in front of the override.

Before
@Override
void eat() { ... }
After
@Override
public void eat() { ... }
Compile

A child method called through a parent variable

See it
java: cannot find symbol
  symbol:   method run()
  location: variable h of type Human

The variable's type decides what you may call, not the object inside. Human has no run(), even though this object is a Caveman.

FixCheck the type with instanceof, cast to Caveman, then call run().

Before
Human h = new Caveman(...);
h.run();
After
Human h = new Caveman(...);
if (h instanceof Caveman) {
    ((Caveman) h).run();
}
Compile

A parent object in a child variable

See it
java: incompatible types: Human cannot be converted to Caveman

The sentence "a Human is a Caveman" is not true, so Java will not copy it across without being told. The arrow of inheritance only goes from child to parent.

FixIf the object really is a Caveman, cast it, ideally after an instanceof check.

Before
Caveman c = h;
After
if (h instanceof Caveman) {
    Caveman c = (Caveman) h;
}
Compile

A cast or instanceof between classes with no family link

See it
java: incompatible types: Caveman cannot be converted to ModernPerson

Caveman and ModernPerson are siblings: both extend Human, neither extends the other. The same error appears for s instanceof Human when s is a String (String cannot be converted to Human).

FixCast only along the line of parents and children. Test or cast through the parent variable, not a sibling.

Before
Caveman c = new Caveman(...);
ModernPerson z = (ModernPerson) c;
After
Human h = new Caveman(...);
if (h instanceof ModernPerson) { ... }
Compile

An overload called through a parent variable

See it
java: method eat in class Human cannot be applied to given types;
  required: no arguments
  found:    int
  reason: actual and formal argument lists differ in length

eat(int n) in Caveman is a second method, not an override, so Human never learned about it. Through a Human variable only eat() exists.

FixOverride with the same parameters, or cast to Caveman to reach the new method.

Before
Human h = new Caveman(...);
h.eat(5);
After
Caveman c = new Caveman(...);
c.eat(5);
Compile

new on an abstract class

See it
java: Asset is abstract; cannot be instantiated

An abstract class is an idea too general to build. It exists to be extended, never to be created with new.

FixCreate a concrete child, such as House. The variable can still be typed Asset.

Before
Asset asset = new Asset("Land", 2023, new BigDecimal("1000.00"));
After
Asset asset = new House("5 bedroom", 2023, new BigDecimal("400000.00"), "123 El Street", 5000, 5);
Compile

A child leaves the abstract method empty

See it
java: House is not abstract and does not override abstract method getValue() in Asset

getValue() is a blank the parent left on purpose. A child that is not abstract itself must fill it. The same message appears for a method marked abstract inside a class that is not.

FixOverride the method in the child, or mark the child abstract too if it is still too general.

Before
public class House extends Asset {
    // no getValue()
}
After
public class House extends Asset {
    @Override
    public BigDecimal getValue() { ... }
}
Compile

An abstract method with a body

See it
java: abstract methods cannot have a body

An abstract method is only a signature. If you write curly braces, it is no longer abstract.

FixEnd the line with a semicolon, or drop abstract and keep the body.

Before
public abstract BigDecimal getValue() { return BigDecimal.ZERO; }
After
public abstract BigDecimal getValue();
Runtime

ClassCastException

See it
Exception in thread "main" java.lang.ClassCastException: class com.pluralsight.Human cannot be cast to class com.pluralsight.Caveman (com.pluralsight.Human and com.pluralsight.Caveman are in unnamed module of loader 'app')
	at com.pluralsight.Main.main(Main.java:5)

The cast compiled because Caveman is a child of Human, but at run time the object is a plain Human. A cast promises; it does not change the object. The two class names in the first line say which object and which cast.

FixAsk first with instanceof, then cast.

Before
Human h = new Human();
Caveman c = (Caveman) h;
After
Human h = new Human();
if (h instanceof Caveman) {
    Caveman c = (Caveman) h;
}
Quiet bug

A misspelled override with no @Override

See it
(no message) the parent's version runs:
I am a Human and I am Hungry!

Without @Override, eet() is just a new method next to the inherited eat(). Nothing is wrong as far as the compiler knows, so a Caveman still eats like a Human.

FixWrite @Override on every override. The typo then becomes a compile error you can see.

Before
public void eet() { ... }
After
@Override
public void eat() { ... }
Quiet bug

Human tested first in an instanceof chain

See it
(no message) every object prints:
This is a Human

A Caveman is also a Human, so instanceof Human is true for all of them and the chain stops at the first branch.

FixAsk about the most specific types first and Human last.

Before
if (person instanceof Human) { ... }
else if (person instanceof Caveman) { ... }
After
if (person instanceof Caveman) { ... }
else if (person instanceof ModernPerson) { ... }
else if (person instanceof Human) { ... }

Messages were produced by compiling and running small samples on Java 17, package com.pluralsight. The line numbers in your own message will differ.
