User Stories

Eight requirements for a hardware store app, turned into stories: who wants it, what they want, and why.

What you are building

A file of user stories for a Hardware Store application. Each requirement becomes one or more stories in the shape As a ..., I want ..., so that ..., written for one real user: a customer, the store owner, the warehouse worker.

No project and no code. The requirements are vague on purpose; your stories should not be. Some requirements need a story per type of user.

What a finished story looks like

the workbook's example
Requirement: Display products list User story: As a customer, I want to view a list of products, so that I can determine what I want to buy.

Your stories are in your own words and will differ. One requirement can give two stories.

Where people get stuck

  • No benefit. The story stops before so that. Without the why, nobody can tell if the feature does its job.
  • It is a developer task. A table, a class, a button. A story says what the user gets, not how it is built.
  • "We" left as the role. We is not a user. Name who: the store owner, the warehouse worker.

The one idea

A requirement says what the system does; a story says what a person gets. Who, what, why, in the user's words, specific enough that a developer can build it without asking you.
