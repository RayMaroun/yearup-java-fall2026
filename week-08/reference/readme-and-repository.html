Capstone 2 · Finish

README and Repository Checklist

Everything your capstone text asks for besides the running program: the repository, the board, the commits, the class diagram and the README. Tick a step when its "done looks like" is true on your screen.

Your own job this timeThere is no class time for the setup in this capstone. You create the repository, the board and the README yourself, before the build week starts.
Where it comes fromThe "Setup" page and the "Repository" part of "Other General Project Requirements" in your capstone text. This page turns them into steps.
Finish it earlySteps 1 to 5 belong to the first days. Steps 6 to 9 are your last hour before you submit, and you do them again after every big change.

Steps0 of 9

    1

    A public repository with a meaningful name

    before the build week

    Do

    1. Create the project in your capstones folder, the way you did for Capstone 1: IntelliJ, New Project, Maven, Java 17, group com.pluralsight.
    2. Give it a name that says what it is: the name of your shop, for example deli-cious. Not a generic name such as capstone-2.
    3. In IntelliJ: Git, GitHub, Share Project on GitHub. Leave Private unticked, so the repository is public. Use the same name as the project.

    Done looks like

    Your repository page on GitHub shows the name of your shop and the word Public next to it. Someone who reads only the name knows what the project is.

    Watch out

    • A private repository cannot be opened by anyone else. Check the badge next to the name.
    • The target folder must not be pushed. Keep the .gitignore IntelliJ creates.
    2

    A project board with user stories

    A User StoryThe Project Board

    Do

    1. On GitHub, open your repository, then Projects, New project, Board. Columns Todo, In Progress, Done.
    2. Read the requirements of your text and write one user story per thing the customer can do: start a new order, add each kind of product, check out, confirm and get a receipt, cancel. Add one card for the class diagram and one for the README.
    3. Each card in the shape you learned: As a ..., I want ..., so that ... Under it, two or three acceptance criteria taken from the text's own words.
    4. While you build, move the card you work on to In Progress, and to Done when it works.

    Done looks like

    The board is linked to your repository and holds a card for every screen and rule of your text. By Demo Day, the cards you finished are in Done.

    Watch out

    • A story says what the customer gets, not what you will code. If a card names a method, it is a task, not a story.
    • One feature per card. "The whole order" is too big for one card.
    3

    A commit for each meaningful piece of work

    The Commit Messageevery day of the build

    Do

    1. Commit each time one small piece works: one product with its price, one screen, the receipt file, the README. In IntelliJ: the Commit panel, tick the files, write the message, Commit and Push.
    2. Each message follows the course convention: type: what changed (feat, fix, docs, refactor, chore), a blank line, then bullets on what you did. The shape is on The Commit Message page.
    3. Push at the end of every day, at least. A commit that is only on your laptop is not in your repository.

    Done looks like

    The commit list on GitHub reads like a diary of the week: many small commits, each with a type and a clear subject, spread over the build days.

    Watch out

    • One giant commit on the last day, or messages such as "update" and "changes", hide all your work.
    • New files show as unversioned in the Commit panel. Tick them, or they are left behind.
    4

    The diagram file in your project

    Class Diagram Guide

    Do

    1. In diagrams.net, File, Save as, and pick your project folder: the one that holds pom.xml. Name the file class-diagram.drawio.
    2. From now on, open the diagram from that file, so every change lands in your project and gets committed with your code.

    Done looks like

    In IntelliJ's Project panel, class-diagram.drawio sits next to pom.xml. On GitHub, it is in the file list of your repository.

    Watch out

    • A diagram saved in Downloads, on the Desktop or only in your browser is not in your project, so it is not in your repository.
    • The capstone asks for the diagrams.net file itself, not only a picture of it.
    5

    A picture of the diagram in images

    Class Diagram Guide

    Do

    1. Create a folder named images in your project folder, next to pom.xml.
    2. In diagrams.net: File, Export as, PNG. Export the whole page. Save it into images as class-diagram.png.
    3. Each time you change the diagram, export again over the same file name, so the picture stays current.
    your-shop/ class-diagram.drawio the file you can still change images/ class-diagram.png the picture the README shows pom.xml README.md src/

    Done looks like

    Opening images/class-diagram.png shows your whole diagram, every box readable, nothing cut off at the edges.

    Watch out

    • No spaces in file names, and all small letters. Class Diagram.PNG is the start of a broken picture in step 7.
    • A selection exported instead of the page leaves boxes out.
    6

    The README, from the course template

    Your README

    Do

    1. Copy the template from the public repo (templates/readme-template.md) to README.md at the root of your project, next to pom.xml. Replace every comment with your own text.
    2. The text asks for four things: what the project is, its main features, how to run it, and the picture of your class diagram. The template's sections, for this capstone:
      • fillTitle and one line, Description of the Project: your shop and what the application does.
      • requiredClass Diagram. The template marks it optional; in this capstone it stays. Keep its one line, it shows the picture from step 5.
      • fillFeatures: one bullet per thing the application can do, in the order of your menus. Mark a bonus as a bonus.
      • fillUser Stories: the same text as the cards on your board.
      • fillSetup, Prerequisites and Running the application: put the name of your class that has main in place of the placeholder.
      • your callData and configuration: optional. Your program writes receipts to a receipts folder, so a line about it helps a reader. If you leave it out, delete the heading too.
      • fillTechnologies Used, Demo (screenshots of your screens in images), A piece of code I am proud of, Future Work, Resources, Author.
      • your callThanks: up to you.
    3. The one line of Markdown that shows the picture, as it already is in the template:
      ![Class Diagram](images/class-diagram.png)

    Done looks like

    No comment from the template is left, no empty heading, no "Project Title". A stranger reading it knows what your shop sells, what the application does and how to start it.

    Watch out

    • The template's comments do not show on GitHub. A section you forgot to fill shows as a heading with nothing under it.
    • List only what works. Half-done features go under Future Work.
    7

    Check the README on GitHub

    after every push of the README

    Do

    1. Commit and push README.md, the images folder and class-diagram.drawio.
    2. Open your repository page in the browser and scroll down to the README. That is what anyone who opens your project sees first.
    3. Look at the class diagram picture, the screenshots, the headings.

    Done looks like

    The README shows under the file list, the class diagram picture appears in full, and every screenshot loads.

    Watch out

    • A broken picture icon means the path does not match the file. Compare letter by letter: folder name, file name, and the capital letters. GitHub sees Images/Class-Diagram.png and images/class-diagram.png as two different files, even when your laptop does not.
    • Not pushed means not there. If the picture is missing from the file list, it was never committed.
    8

    The diagram matches the code

    Class Diagram Guide

    Do

    1. Put the README picture and your code side by side. Go box by box: every class in the code is a box, every box is a class in the code, with the same names.
    2. Anything that changed while you built, change in the .drawio file, export the PNG again over the old one, commit and push both.

    Done looks like

    Someone holding only the picture would find every class of your project in it, with the names you used in the code.

    Watch out

    • The text says to keep your diagram current. The Wednesday version is a starting point, not the final one.
    • Changing the .drawio without a new export leaves the README showing the old picture.
    9

    Clone it into a new folder and run it

    The Receipt Filethe last check

    Do

    1. Copy the address of your repository from the green Code button on GitHub.
    2. In IntelliJ: File, New, Project from Version Control. Paste the address and choose a new, empty folder, not your capstones folder.
    3. Follow your own README's "Running the application", word for word. Place one order to the end and confirm it.

    Done looks like

    The fresh copy runs without any change, the order goes through, and its receipt file appears in the receipts folder of that copy. It works for someone who only has your repository.

    Watch out

    • A file that exists only on your laptop, never committed, breaks here. Commit it and try again.
    • Close the copy afterwards and keep working in your own project, so your next commit goes to the right place.

    If you only remember one thing

    Your repository is what other people see of your project. A clear name, a board, a commit history that tells the story, a README with your diagram in it, and a copy that runs for someone who only has the link.
