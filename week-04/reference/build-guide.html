Build Guide

Thirteen steps, in the order of the TODOs in the starter. Each step says what to do, what it looks like when it works, what usually goes wrong, and what to commit. Tick a step when its "done looks like" is true on your screen.

Before you startRead the PDF in Brightspace twice. Open the Requirements Checklist next to this page.
Work in this orderBoard and stories first, then the code one TODO at a time, README last. Every step uses the one before it.
Commit after every stepOne commit per step is the "commit history" the spec asks for, and it saves your work when something breaks.
Stuck for 20 minutes?Bring the step number and what your screen shows to office hours. "Step 6, the line goes in the file but the next run does not load it" gets you an answer fast.

    A User StoryThe Project BoardFri Oct 30, in class

    Do

    1. Create a GitHub project board on the repository, columns Todo, In Progress, Done.
    2. Read the spec and write one user story per feature: add deposit, make payment, ledger all, deposits, payments, each of the four date reports, search by vendor, custom search, README. Each story is a card in Todo.

    3

    The Transaction class

    One Line, One Object

    Do

    1. Read one line of the file: date|time|description|vendor|amount. One line is one object, so the class has five fields, one per piece.
    2. Pick the type of each field by asking what the rest of the app will do with it later: compare it, sort by it, add it up, print it. Text is the wrong answer for most of them.
    3. Write the constructor that takes all five, and a getter for each field.
    4. Write a toString that returns the line exactly as it sits in the file, pipes and all, amount with two decimals. One line of the file in, one object, the same line out.

    Done looks like

    The project compiles and the red in FinancialTracker is gone. Running it shows the Home menu. In a scratch test, building one Transaction and printing it gives back the file line you started from.

    Watch out

    • A field kept as text is the mistake that comes back in steps 7, 9 and 10. Decide the types now, not when the report breaks.
    • Same name and same package as the starter expects: Transaction in com.pluralsight.
    • 4400.0 is not the file format. Two decimals, the way money was printed in week 1.

    Commit

    Add Transaction class
    4

    Load the file at start

    Load Then AppendFrom Lines to Objects

    Do

    1. If transactions.csv does not exist, create it empty. The spec says the app creates the file.
    2. Read it line by line until there are no lines left, the way the week 3 exercises read their files.
    3. For each line: split it into its five pieces, turn each piece into the type your field needs, build a Transaction, add it to the list.
    4. File work can fail. Handle that, and close what you open.

    Done looks like

    A temporary print of the list after loading shows 21 lines with the starter file, each one equal to its line in the file, because toString is the file format. Delete the file, run again: it is created empty and the app still starts.

    Watch out

    • The pipe is a special character for split. If every character becomes its own piece, look up how to escape it.
    • Dates parse only when the text is exactly yyyy-MM-dd. A space at the end of a line breaks it.
    • The file path is relative to the project root, which is where IntelliJ runs the app.

    Trace the three menus

    Menu Flow Map

    Do

    1. Nothing to write in this step. The starter already has the Home loop in main, the Ledger loop and the Reports loop, each a while with a switch over the letter typed.
    2. Run the app and press every letter: D, P, L, then A, D, P, R, H, then 1 to 6 and 0, then X. Read the case that each letter runs. Most of them call a method that is still a TODO.
    3. Write down which TODO method each letter lands in. That list is the rest of this guide.

    Done looks like

    You can say, without looking, which method D calls on Home, which one A calls on Ledger, and why H brings Home back.

    Watch out

    • The starter reads every answer with nextLine and one Scanner that is passed into the methods. Keep it that way. A second Scanner on System.in, or a nextInt in the middle, makes the menus skip inputs.
    • The Home title says "Welcome to TransactionApp". Changing it is the bonus in step 13, not now.

    6

    Add a deposit

    Deposit or PaymentLoad Then Append

    Do

    1. Fill in addDeposit. Its comment in the starter says what to ask: one text for the date and time in the format yyyy-MM-dd HH:mm:ss, then the description, the vendor, the amount.
    2. Turn the text into your date and time types (week 3, date patterns). Check the amount is positive; if not, say so and ask again.
    3. Build the Transaction, add it to the list, and add one line to the end of the file. The line is the object's toString, that is what step 3 built it for.

    Done looks like

    Open transactions.csv after a deposit: one new line at the bottom, same format as the others, nothing else changed. Run the app again and the count from step 4 is one higher.

    Watch out

    • If the file ends up with only the new line, your writer replaced the file instead of adding to it. Find out how to open it so it adds. Step 4's count tells you at once.
    • Write a line break after the line, or the next deposit glues to this one.
    • A date typed in the wrong format throws. Catch it and ask again instead of crashing.

    Make a payment

    Deposit or Payment

    Do

    1. Fill in addPayment. Same questions as the deposit, the user types a positive amount.
    2. Before storing, make the amount negative. That sign is what makes it a payment; there is no other field for it.
    3. Same append to the file. If steps 6 and 7 share one method with a flag, better.

    Done looks like

    The new line in the file ends with a minus amount, for example |-48.30, and loads back as a negative number next run.

    Watch out

    • Do not ask the user to type the minus. If they do anyway, reject it like any non-positive amount.

    8

    Ledger: All

    Menu Flow Map

    Do

    1. The Ledger menu is already in the starter. Fill in displayLedger: every transaction, one per line, in columns: date, time, description, vendor, amount. printf with widths keeps the columns straight.
    2. Newest first. The starter's TODO says so. Decide how you get that order, and check it with the top line.

    Done looks like

    The top line of A is the latest date in the file (with the starter file, 2026-11-03). Columns line up. H brings the Home menu back.

    Watch out

    • "Newest first" is in the spec and is the first thing Raymond checks. Oldest first is the most common miss.
    • Negative amounts need room for the sign in the column width.
    • Do not print the toString here. That is the file format, the ledger is a table for people.

    10

    The four date reports

    Date Range Reports

    Do

    1. The Reports menu is already in the starter, with cases 1 to 4 empty and a helper filterTransactionsByDate(start, end) that is a TODO. That shape is the idea: every date report is the same question, is the transaction date between a start and an end, both included.
    2. Fill in the helper first: loop the list, print the rows inside the range, say so when none match.
    3. Then each case computes its two dates and calls the helper. Work out the four pairs on paper before you code them, starting from today. The Date Range Reports picture shows where each range starts and ends.

    Done looks like

    With the starter file in the first week of November: Month To Date shows the two November rows, Previous Month the three October rows, Year To Date every 2026 row, Previous Year every 2025 row. An empty result prints a message, not nothing.

    Watch out

    • A transaction on the first of the month must count. Check what the date comparison you use does with the boundary day.
    • Previous Month in January is December of last year. Test that case.
    • Do not compare dates as text.

    Commit

    Reports: month to date, previous month, year to date, previous year

    Custom search (bonus)

    Custom Search Pipelineonly after 1 to 11 work

    Do

    1. Option 6) Custom Search is already on the Reports menu and calls customSearch, a TODO. Ask for five values in this order: start date, end date, description, vendor, amount. Enter with nothing typed means "no filter".
    2. The two helpers at the bottom of the starter, parseDate and parseDouble, are TODOs too and return null. Their comments tell you what null stands for. Fill them in and use them for the dates and the amount.
    3. One loop over the list. Work out what "blank means no filter" has to mean for each of your five tests.

    Done looks like

    All five blank prints every row. Vendor only prints the same as step 11. Start and end dates only prints the same as a date report with those dates. Combined filters narrow the rows further, never widen them.

    Watch out

    • Filters combine with AND. A row has to pass every filter that was given.
